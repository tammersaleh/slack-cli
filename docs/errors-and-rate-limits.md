# Errors, exit codes, and rate limits

Measurements and reasoning behind the rules in `CLAUDE.md`. `CLAUDE.md` holds the current rule for each topic. This file holds how it was found.

## ClassifyError always returns a stable code

`api.ClassifyError` never puts raw Go error text in `output.Error.Err`. That field is the value a paginated command copies into `_meta.error`, which SPEC documents as the field a consumer branches on, and `_meta` has no room for anything else - so it is a snake_case code in every case and the original text goes in `Detail` (stderr only). The **fallback itself** is a code (`unknown_error`), which is what makes the guarantee hold for error shapes nobody enumerated; the recognizers above it exist to name failures worth branching on, not to keep the field clean. Verified live 2026-07-27 that the field previously leaked, in order of how much they gave away: `json: cannot unmarshal string into Go struct field .channels of type []slack.Channel` (Go type names), `Post "https://slack.com/api/conversations.list": context deadline exceeded` (request URL), `slack server error: 500 Internal Server Error`, `invalid character '<' looking for beginning of value`. Codes added: `timeout` (`errors.Is(err, context.DeadlineExceeded)` - **must** be `errors.Is`, since the HTTP client wraps the deadline in a `*url.Error` mid-request while `FetchPage`'s pre-flight `ctx.Err()` returns it bare, and both reach here), `http_error` (`slack.StatusCodeError`, a non-200 that is not a 429 - slack-go turns 429 into `RateLimitedError` first), `parse_error` (`*json.SyntaxError`/`*json.UnmarshalTypeError`; reachable with Slack behaving normally - a captive portal or proxy answering 200 with HTML - and the code was already in use in cmd/saved.go, so no new vocabulary). All keep exit 1: `ExitNetwork` reads as "the network failed", which a self-imposed `--timeout` is not, and moving a documented exit code buys a consumer nothing. Not added: `context.Canceled` - there is no signal handling and `cancel()` is only deferred past the end of `Run`, so it is unreachable; it would land in `unknown_error` with its text in the detail. `unknown_error` deliberately is not `internal_error`, which is a real Slack API error string that passes through unchanged - two failures must not share a code. The invariant is pinned by `TestClassifyError_ErrIsAlwaysAStableCode` (regex over a corpus of every known shape), which catches a new leak that per-case tests cannot.

## The two rate-limit wire shapes

A rate limit has two wire shapes and `api.RateLimitWait` is the one place that recognizes both: slack-go's `*slack.RateLimitedError` (HTTP 429 with `Retry-After`) and a typed `SlackErrorResponse` whose code is `ratelimited` or `rate_limited` (a 200 with `ok:false`; `users.profile.get` limits this way, with no header to read). The shared `retry` loop and `ClassifyError` both ask it, so a body-level limit retries at the one-second floor and classifies `rate_limited`, exit 3. Slack's `ratelimited` spelling never reaches `error` or `_meta.error`. Before 2026-11-10 the body shape took the generic Slack-error branch: exit 1, code `ratelimited`, never retried, and `isSystemicErr` carried both spellings to paper over it. The floor is one second per wait, four waits: field reports say `users.profile.get` needs about 15s to refill, so a drained bucket still exhausts the budget and exits 3. Longer backoff for the header-less shape and cross-call pacing are open (`todo/user-info-full-aborts-mid-stream-with-no-meta-trailer.md`).

## Rate limits on internal-API calls

Internal-API calls report rate limits like the public ones. `postInternal` (internal/api/client.go, the one body behind `PostInternal` and `PostInternalForm`) returns `*slack.RateLimitedError` for an HTTP 429 and for an `ok:false` envelope naming the limit, with `RetryAfter` read from the header and zero when absent (the retry loop floors it at one second). It deliberately does not mirror slack-go's `checkStatusCode`, which only builds a `RateLimitedError` when a 429 carries `Retry-After` and otherwise never retries. `saved list` therefore retries through `FetchPage` with no change to the command, and a single-shot internal call exits 3 as `rate_limited` with Slack's wait in `detail`. `postInternal` itself makes one attempt: retry is the caller's choice, because not every internal write is safe to repeat. `Client.RetryInternal`/`RetryInternalForm` wrap the two helpers in `api.Call` for the calls that are: the single-shot reads (`users.channelSections.list`, `saved.list` in `saved counts`, `client.counts`, `admin.roles.entity.listAssignments`, `files.info`, `drafts.list`, `lists.records.info`) and two set-state writes, `users.channelSections.set` and `.channels.bulkUpdate` (a repeated insert of a channel already in the target is ignored, and both commands verify by re-reading). Left single-shot on purpose: `users.channelSections.create`, `drafts.create`/`update`/`delete`, and every `lists.*` write. A 429 means Slack did not run the request, so retrying any of them is probably safe, but that is an inference, and a create that did run twice makes two objects. The paginated internal calls stay on plain `PostInternal*` because `FetchPage` already retries them; wrapping them again would multiply attempts. A test that makes a retried call fail with `ratelimited` costs four seconds of floor waits, so use another code unless the retry is the point. A non-200 with no envelope is `slack.StatusCodeError` (`http_error`) rather than `parse_error`. Which shape Slack really uses for a limited internal method is still not captured from the wire (the one field report, `section move` under a 406-move bulk run, showed only the classified stderr), which is why both are handled.

## abortWithTrailer

`abortWithTrailer` (cmd/abort.go) is how a multi-input command that is not a `streamPages` stream stops on a fatal error: `{"_meta":{"has_more":true,"error":"<code>","error_count":N}}`, no cursor, then the classified `*output.Error` to stderr. Every multi-input command uses it. Until 2026-11-10 `user info --full` returned straight out of its loop on a systemic error, so a rate-limited 45-input run printed 3 good rows and no trailer, and a caller filtering out `_meta` read that as "3 of these people exist". The bulk commands that abort on a non-1 exit code had the same gap and use it too (`message get` in both its history and fallback branches, `message permalink`, `reaction list`, `channel info`, `file info`, `dnd info`, `presence get`, `draft delete`); `TestBulkCommands_FatalAbortWritesTrailer` pins them. Those commands' calls are still one-shot slack-go calls with no retry, so one rate limit ends the run. All of them decide fatal-versus-row with `isSystemicErr`, not an exit-code compare, because `timeout` classifies exit 1 yet kills every remaining input: the exit-code form printed one `timeout` row per input. `status get` shares `user info`'s lookup (`resolver.FetchUser`, `userLookupFailed`). Input resolution in `user info`, `manager-chain`, `status get`, `presence get`, `dnd info`, and `channel info` happens up front (`resolveInputs`), and a failed lookup there aborts through `abortWithTrailer` with an error count of 0 before any row. The `users.info` fallback is an `api.Call` like the profile fetch. `user info`'s per-input rows now go through `userLookupError`: only Slack's not-found codes become `user_not_found`, anything else keeps its own code (both lookups used to label every non-systemic failure `user_not_found`). The `users.profile.get` fetch for `--full` and `manager-chain` is `fetchUserProfile`, an `api.Call`, so it retries and shows up in `--trace` as `call` events. Retry is not pacing: the method limits after about three calls and the bucket is shared across processes, so a long `--full` list still exhausts five attempts one second apart. Pacing is undecided (`todo/user-info-full-aborts-mid-stream-with-no-meta-trailer.md`).

## missing_scope

`missing_scope` is in `api.authErrors`, so it exits 2 everywhere, as SPEC's exit-code list always said. It stays out of `nonResumableErrors` (a granted scope makes the same page fetchable, so the trailer keeps `has_more:true` and the cursor). `no_permission` and `not_allowed_token_type` stay exit 1: `no_permission` can describe one target rather than the token, and neither is fixed by logging in. `cli.ClassifyError` gives `missing_scope` its own hint (`missingScopeHint`) because the generic re-auth hint is wrong for a desktop session token: the OAuth flow grants the scopes `botScopes` requests now, while a session token carries whatever Slack gives the account and logging in again adds nothing. Side effect to know: the bulk commands that abort on a non-1 exit code (`message get`, `message permalink`, `reaction list`, `channel info`, `file info`, `dnd info`, `presence get`, `draft delete`) now treat `missing_scope` as fatal instead of a per-row error, which is right - a scope problem repeats for every input.
