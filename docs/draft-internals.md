# Draft internals

Measurements and reasoning behind the rules in `CLAUDE.md`. `CLAUDE.md` holds the current rule for each topic. This file holds how it was found.

## The conditional two-client split in draft create

`draft create` needs the two-client split too, but **conditionally**: only a name-shaped channel recipient builds the workspace client (`resolve.ChannelInputNeedsLookup`, which mirrors `ResolveChannel`'s early returns so client selection can't drift from resolution behavior); `drafts.create` always rides the session client. Until 2026-08-31 the one session client went to `NewResolver`, and on Enterprise Grid the org token answers `enterprise_is_restricted` on both `users.conversations` and `conversations.list` - so **no `#name`/bare-name channel could ever resolve**, always erroring `channel_not_found` with a browse-the-channel-list hint that pointed away from the real cause (that flattening was `channelResolveError`, fixed 2026-11-10: a failed lookup now keeps its own code). The failure was verified live 2026-08-31, and the fix the same day (a `#name` resolved via users.conversations on the workspace client, the draft landed on the same channel ID the report's ID-form control used, then deleted); the routing is pinned by distinct-credential mocks plus mutation testing. The split is conditional for the same reason `saved list` builds its public client only under `--enrich`: ID/URL recipients resolve locally and must keep working on an org session credential alone, and requiring `NewClient` unconditionally would fail `not_authed` in a multi-credential setup with no `SLACK_WORKSPACE` selected. **User (`@name`/email) resolution deliberately stays on the session client** to preserve the org-context behavior that already worked: moving it to a workspace credential is an unverified scope change that could narrow directory visibility or change which accounts a shared name ranks, and a workspace OAuth bot lacks `users:read.email`. Tests: `TestDraftCreate_TokenRouting` (forces the conversations.list fallback with an empty member page so both resolution endpoints' tokens are observed; fails on the one-client build with the live error), `_UserRecipient` (pins users on the session token), `TestDraftCreate_OrgOnlyCredential` (IDs and invalid_input precedence survive with no workspace credential; a name gets `not_authed`, not the old lie), `TestDraftCreate_SessionAuthHintSurvivesSplit` (drops of the authMethod capture/restore fail it; green pre-split by design). Two claims from the 2026-08-31 bug report did not hold: the failure was never silent (exit 1 plus a JSON error on stderr; the reporting harness discarded both), and the "top-level `channel_id: null`" output claim was jq manufacturing null for a key `formatDraft` never emits.

## Draft ghosting

Draft ghosting (`is_deleted=true` appearing on the server within seconds of create) is caused by Slack Desktop's Drafts-panel composer reconciliation: any server-side draft whose `blocks` array does not contain at least one `rich_text` block with non-empty `elements` gets tombstoned. Host, UA, TLS fingerprint, and `last_updated_client` stamp do not matter - block content does. `validateBlockShapes` (cmd/draft.go) rejects such payloads before they ship. The `auto-replace` path (`createReplacement` for tombstoned drafts) still exists as defense-in-depth for races where Desktop already marked a draft deleted between our `drafts.list` and `drafts.update`. Full write-up in `docs/draft-messages.md`.

## Draft stripping and the payload model

Draft stripping (distinct from ghosting): Slack Desktop's Drafts compose editor silently discards every non-`rich_text` top-level block when the user opens the draft to edit. A `[rich_text, section]` payload ships fine and the draft isn't tombstoned, but the user only ever sees the rich_text content. `validateBlockShapes` rejects any top-level block other than `rich_text`, `header`, and `divider` with `invalid_blocks` for this reason - section/context alongside rich_text is silent content loss (`header` and `divider` were in that list until 2026-11-06; see the header and divider bullets below). Tables are the exception worth knowing: a `table` block is stripped in *top-level* blocks but SURVIVES in `attachments[].blocks[]`, rendering as an editable Table card - so the top-level rejection steers callers to attachments / `--table`. `data_table` (the interactive variant) is NOT draftable: it's stripped from the compose editor and a data_table-only draft is tombstoned, even in an attachment - so it's rejected outright (both verified end-to-end 2026-05-29; see docs/draft-messages.md). Draft payload model: stdin is a bare blocks array OR `{blocks, attachments}`; create/update carry an `attachments` form param; update is tri-state per field (provided replaces, absent preserves, `attachments:[]` clears); `--table FILE` builds a table attachment from CSV/TSV (header row bold, `--no-header` to disable); `createReplacement` carries attachments (and, since 2026-11-16, `file_ids`) across the tombstone path; a draft survives reconciliation with a rich_text body OR a table attachment (attachments-only is fine). Caller-supplied attachment blocks are restricted to `table` (`validateAttachmentBlocks` rejects `data_table`); existing attachments round-trip verbatim. The canonical Slack-editor shape is a single top-level `rich_text` containing sibling `rich_text_section`/`rich_text_list`/`rich_text_preformatted`/`rich_text_quote` containers, with `header` and `divider` blocks between runs when the message has headings or horizontal rules; multiple adjacent top-level `rich_text` blocks get flattened by Desktop before absorption runs.

## Section-before-container absorption

Section-before-container absorption (list/preformatted/quote): a `rich_text_section` directly followed by `rich_text_list`, `rich_text_preformatted`, or `rich_text_quote` gets its content absorbed into the following container (heading glues onto first bullet / merges into the code block / glues into the quote) unless the section's last text inline ends with `\n`. Slack's own compose editor sidesteps this by always emitting the trailing newline; agent-built payloads must too. `validateBlockShapes` enforces it: the section's element stream must terminate with a text inline whose `text` ends with `\n` (trailing empty text inlines are ignored). Non-text trailing inlines (link, emoji, user, channel, broadcast) don't satisfy the rule; append a final `{"type":"text","text":"\n"}`. The check spans top-level rich_text boundaries because Desktop flattens them. The reproduction matrix (2026-05-15, both negative and positive) lives in `docs/draft-messages.md`.

## --markdown conversion

`draft create --markdown` / `draft update --markdown` convert Markdown to header, divider, and rich_text blocks via `internal/mdblocks` (goldmark + GFM strikethrough, linkify, and table extensions), then feed the result through `parseDraftPayload` so `validateBlockShapes` is the backstop - `invalid_blocks` after a successful conversion is a converter defect, `invalid_markdown` (always `line N:`) is the caller's. Design rules that matter: a `header` block per heading, a `divider` block per thematic break, and exactly one top-level `rich_text` per run of containers between them, never an empty `rich_text` and never two adjacent (Desktop flattens multiples; a document with neither is one block); a nested list **splits** its parent into separate `rich_text_list` containers in source order (`parent A / child / parent B` is three containers, indent 0/1/0) with ordered `offset` continuing the count, because a list cannot hold a list; headings are `header` blocks (see the header bullet below), and the converter still ends a paragraph before one with `\n` for uniformity - the header supplies its own spacing, so the newline makes no visible difference (inspected 2026-11-06); the Slack tokens (`:emoji:`, `<@U>`, `<#C>`, `@here`) are **goldmark inline parsers**, not a regex over decoded text, which is what keeps `\:wave:` and code spans literal for free and gives errors a source offset; goldmark leaves backslash escapes and entities in the raw text segment (its HTML renderer resolves them), so `textOf` must unescape - the first build emitted a literal `\*`. Symbolic `@name` is still **rejected** (use `<@Uxxx>`). Name resolution has been deterministic since 2026-11-10, so that is no longer the blocker; what is left is design, in `todo/markdown-at-name-mentions-are-rejected.md`: the converter is pure and `--print-payload` promises zero API calls, and prose gives no end to a multi-word name; `@` after a word character or `<` is literal so emails and an escaped `\<@U…>` survive. Slack's `drafts.create` rejects an **empty text inline** (`{"type":"text","text":""}`) with `invalid_message` (verified live 2026-10-16), so an empty `-` item or `>` quote is an `invalid_markdown` error, not a placeholder. Blank stdin under `--markdown` is "nothing provided" (`missing_blocks`, or attachments-only with `--table`), not `invalid_markdown`. `--print-payload` needs `--markdown`, rejects write-only flags, and makes zero API calls - on `update` it shows the submission, not the merged draft. Goldens in `internal/mdblocks/testdata` are exact JSON; `cmd/draft_markdown_shapes_test.go` runs each through `validateBlockShapes`. A list or code block inside a `>` quote is **not nested**: Slack rejects a `rich_text_list` inside `rich_text_quote.elements` (`invalid_message`), and the composer stores a quoted list as a sibling `rich_text_list` with `border: 1` and no `rich_text_quote` at all. `quote` walks its children in source order - paragraph runs flush as one `rich_text_quote` (no border key), lists call `list(v, 0, true)`, code blocks emit a bordered `rich_text_preformatted` - and `border` is a **parameter** threaded through `list`, never converter state, so every nested split and resumed ordered segment carries it and the key is omitted when false. Verified 2026-11-02/03 (self-DM, hand-built probe): quote, bordered lists at indent 0/1, bordered ordered, quote, bordered code round-trip byte-identical, survive 30s, and render under one continuous bar in the Desktop compose box with no glue between the quote text and the first bullet; the composer was not observed emitting bordered preformatted itself, so the code shape rests on rendering alone. The same screenshot showed a bordered ordered list with `offset: 2` rendering as `1.` - the compose box ignores `offset`, at least when bordered. Two goldmark facts that bit: ordered items are numbered by **count**, so `> 3. a` / nested / `> 5. b` resumes at `offset: 3` and the written `5.` is ignored (same formula as `ordered-split`: `max(Start-1,0) + items emitted`); and `lineOf`'s fallback for a segment-less node (an empty fence) must skip `>` markers when the node sits inside a blockquote, or the error names the blank `>` line above. Live-verified 2026-10-16 (self-DM): every construct round-trips `drafts.create` → `drafts.list` byte-identical and survives 25s; Desktop rendering of italic/strike, ordered `offset`, and the heading's blank line was **not** inspected - see `docs/draft-messages.md`.

## Header blocks and the probe module

Header blocks (`{"type":"header","level":1..3,"text":{"type":"plain_text","text":"...","emoji":true}}`) are the compose editor's own big/medium/small headings, read back from a composer-authored draft 2026-11-06 with no `rich_text` beside them and no tombstone - so the earlier "header only: tombstoned" matrix row in `docs/draft-messages.md` is superseded. Probed through the CLI's session client the same day (self-DM, each read back byte-identical modulo the server-assigned `block_id`, alive after 60s): header-only; a header / rich_text / header / rich_text / header mix; `level` omitted (stored without it); `level: 4` (stored as 4); `emoji` omitted (server adds `emoji: true`); `[section without "\n", header, list]` (stored). Rejected server-side with `invalid_message`: `level: 0`, `text.type: mrkdwn`, empty `text.text`. `validateBlockShapes` (cmd/draft.go, `validateHeaderBlock`) mirrors that: `text` must be a `plain_text` object with non-empty text, `level` when present must be an integer >= 1 with no upper bound, `emoji`/`block_id` pass through, a header counts as renderable content (`hasBody`, renamed from `hasRichTextBody`), and a header **is** an absorption boundary - a valid header resets the section-before-container state, so `[section without "\n", header, list]` passes. It shipped as a non-boundary in 5.10.0 because the probe proved storage, not rendering; the Desktop inspection the same day (2026-11-06) showed that payload as paragraph, heading, bullet with no glue, and the `fix:` that relaxed it inverted `TestValidateBlockShapes_HeaderResetsAbsorption`. The rule still applies inside one `rich_text` and across adjacent `rich_text` blocks. The converter (`internal/mdblocks`) emits `header` for ATX and Setext headings with `level = min(level, 3)` (the composer offers three sizes; the clamp is a documented normalization like the dropped fence language), text flattened to plain (`plainText`: bold/italic/strike/code to their text, soft and hard breaks to a space, `:name:` tokens written back as `:name:` text), and rejects as `invalid_markdown` a link (explicit, bare URL, email, or `<url>`), user or channel mention, broadcast, image, or HTML inside a heading - dropping bold is not content loss, dropping a URL is. Items are collected flat (`converter.items`) and grouped by `blocks()` at the end (`topLevelType` names header and divider as the run breakers), so a leading, trailing, or consecutive heading or divider never produces an empty `rich_text`; `applyAbsorptionRule` runs over the flat sequence, so a paragraph before a header still ends with `\n`. Goldens: `heading`, `absorption` (rewritten), `header-mixed`, `header-only`, `header-consecutive`, `header-setext`, `header-clamp`, `header-inline`; `TestGolden_TopLevelShape` pins the block-level invariants. Inspected in Desktop 2026-11-06 (the probe drafts in the self-DM): `level: 4` renders as the small heading, identical to level 3, so the converter's clamp is what the client does anyway; `:tada:` in a header's plain_text renders as the emoji; a paragraph with and without a trailing `\n` before a header looks identical; a header breaks absorption; the `--markdown` draft with levels 1, 2, 3 then paragraphs and a list renders correctly at three sizes. Plan: `docs/header-blocks-plan.md`. To probe `drafts.create` with a payload the validator rejects, do what the 2026-11-06 measurements did: a throwaway Go module in the scratchpad whose module path sits under the repo's (`github.com/tammersaleh/slack-cli/zzprobe`, so Go's internal-package rule lets it import `internal/api` and `internal/auth`) with a `replace` directive pointing at the checkout, a `main` that calls `auth.ResolveCredentials` with `SLACK_WORKSPACE_ORG`, builds `api.New` with `WithUserToken` and `WithCookie`, and sends the same form `PostInternalForm` would - `blocks`, `destinations`, `client_msg_id`, `file_ids: []`, `is_from_composer: true` - against the self-DM. `GOFLAGS=-mod=mod go mod tidy`, build, run, read back with `slack draft list` after 60s, delete the drafts. Out of tree so a feature agent's working tree never sees it. Curl is not a substitute (Grid needs the Chrome TLS fingerprint).

## Divider blocks

Divider blocks (`{"type":"divider"}`) are the compose editor's horizontal rule, read back 2026-11-06 from a composer-authored draft as `rich_text, divider, rich_text, divider, rich_text` with a server-assigned `block_id` on each divider and no tombstone - so the May "divider only: tombstoned" and "[section, divider]" matrix rows and the "no `<hr>` in the DOM" observation in `docs/draft-messages.md` are superseded. Probed through the CLI's session client the same day (self-DM, byte-identical modulo `block_id`, alive after 100s): divider-only; `[section without "\n", divider, list]`; `[divider, rich_text, divider, divider, header, divider]` (a double divider is stored as two). `validateBlockShapes` accepts `divider` as a third top-level type checking only `type` (every other field passes through - the server validates), counts it as renderable content (`hasBody`), and names all three types in the generic rejection and `errNoRenderableContent`. A divider is **not yet** an absorption boundary: Desktop rendering is pending a check, so the section-before-container state carries across it and `[section without "\n", divider, list]` is `invalid_blocks` (conservative; flip to the header treatment - reset `prevElem`/`prevSection` - once Desktop shows no glue). The converter (`internal/mdblocks`) maps `*ast.ThematicBreak` (any CommonMark spelling: `---`, `***`, `___`, spaces allowed) to a divider item, and `blocks()` flushes the rich_text run at it exactly as at a header; `applyAbsorptionRule` is unchanged, so a paragraph before a divider still ends with `\n`. A thematic break inside a quote or list item keeps the container rejection. Goldmark fact worth a test: `Title\n---` is a Setext H2, `Title\n\n---` is paragraph then divider (`TestConvert_SetextVersusDivider`); the list-item rejection test uses `***` for that reason. Goldens: `divider-only`, `divider-edges`, `divider-mixed`. Plan: `docs/divider-blocks-plan.md`.

## Draft state

Draft state (2026-11-10 sweep, all mock-verified, no live draft writes). `draftData.IsSent`/`IsDeleted`/`IsFromComposer` are `*bool` and `formatDraft` emits each only when Slack sent it; read them through `sent()`/`deleted()`. Before this, `draft list` filtered on two fields it never printed, so `jq .is_deleted` returned `null` for every row and a caller read an absent key as state. The `draft list` trailer always carries `suppressed_sent`/`suppressed_deleted` (pointer ints on `output.Meta`, zero emitted); a draft hidden by both filters is counted once, under the first that hid it (sent). `--limit` outside 1-100 is `invalid_input` (`draftPageMax`); it used to fall back to 50, so `--limit 200` returned fewer rows than `--limit 100`. A lookup miss with `has_more:true` is `draft_lookup_incomplete`, not `draft_not_found` (the lookup itself is the next bullet). `draft update` refuses a sent draft (`draft_already_sent`), checked right after the lookup and before the tombstone branch, because the replacement path used to hand back an unsent copy of a delivered message. `isDraftTombstoneError` is gone: a failed `drafts.update` (anything `isSystemicErr` does not claim) triggers one more `drafts.list`, and the draft's state decides - sent is `draft_already_sent`, deleted is replaced, live or missing surfaces Slack's error. So `draft_update_invalid` on a draft the list still shows live is now an error, where it used to replace. What `drafts.update` actually answers for a sent draft was never captured; the design does not depend on it. The replacement row carries `replaced_draft_id`, which is in `alwaysKeptFields` (the code reviewer caught that `--fields id` otherwise printed a new id with no sign of the re-key). `draft delete` builds its error row from `oErr.AsItem()` plus `input`; the same hand-built three-key row is still in `dnd`, `presence`, `permalink`, `channel info`, and `file info`. Test helper: `updateRaceMux` (cmd/draft_test.go) serves one draft state on the lookup and another on the re-fetch.

## drafts.list reach

`drafts.list` reach, measured read-only 2026-11-10 with the probe module on an account whose newest 100 drafts were 73 sent, 26 deleted, 1 live (numbers and the full list of parameters tried are in `docs/draft-messages.md`). The page is ordered by `last_updated_ts` descending, `limit` clamps at 100 (omitted is 10), and nothing pages: 18 continuation-shaped names and 4 sort names all returned the same 100 ids. `last_updated_ts=<ts>` is a "changed since" lower bound, still newest-first, so it does not page either. `is_active=true` returns drafts neither sent nor deleted and **filters before the limit** (at `limit=10` it returned a draft outside the plain newest 10), which is the only route past the page. So `draftLookup` (cmd/draft.go) reads the plain 100 and, only when an id is absent and that page was truncated, the active answer once per command. `draft list` in its default mode does the same union: live rows of the plain page, then active rows not already printed, with `has_more` taken from the active answer. With `--include-sent`/`--include-deleted` it is the plain page alone. `--active` was removed, since the default listing is now a superset of it. The plain request stays first on purpose: the one live draft measured was scheduled and `is_from_composer: true`, so whether `is_active=true` covers an unscheduled live draft or a non-composer one is unmeasured, and a union cannot list fewer drafts than the old code did. `suppressed_*` describe the plain page only. `draft_lookup_incomplete` now means "not an unsent draft the lookup can see", fired only when the plain page was truncated and the active answer lacks the id too. `draft delete` rows are `{id, status}` with `deleted` or `already_deleted` (the `channel invite` style): a draft the lookup shows `is_deleted` gets no `drafts.delete` call and exits 0, and a failed delete re-reads the draft and reports `already_deleted` only when it is now marked deleted, never on `draft_delete_invalid`. All of the union, lookup, and delete behavior is mock-tested only (`draftReachMux` in cmd/draft_reach_test.go models the two answers): no draft was written, and the account had no live draft beyond its plain page to list. The probe's `main.go` takes `key=value` form params and prints counts, top-level keys, and per-draft key counts, writing ids to a scratch file for `comm`. Keep it that shape so draft bodies never reach the transcript.

## Draft files

Draft files (`draft create --file`, `draft update --file`/`--no-files`, cmd/draft_files.go; plan and measurements in `docs/draft-files-plan.md`, findings in `docs/draft-messages.md`). Measured 2026-11-16 on a Grid org with a desktop session token, self-DM, probe module, everything deleted afterwards: slack-go's `GetUploadURLExternalContext`, `UploadToURL`, and `CompleteUploadExternalContext` (no channel) work on the session client's `Bot()` and yield a private, unshared file; `drafts.create` accepts `file_ids` with a rich_text body, with `blocks=[]` (the composer's own file-only shape), with two ids on a thread destination (order kept), and with an id already on another live draft; an id that does not exist or whose upload was never completed is `file_not_found`; omitting `file_ids` is `invalid_arguments`; the create response is `{ok, draft, files}`; `drafts.list` carries a top-level `files` array, deduplicated across the page, that omits a deleted file while its id stays in the draft's `file_ids`; `drafts.delete` leaves files in place; `files.delete` on a file a live draft references answers ok and leaves a dangling id. The design rules: `--file` on update **replaces** the list (no flag preserves, `--no-files` clears, both together is `invalid_input`); a file is renderable content, so create skips `missing_blocks`/`errNoRenderableContent` when `--file` is given and `buildIntent` counts kept or to-be-uploaded files on the effective draft (a dangling id counts); paths are checked locally before any request (readable regular file, non-zero size) and `--print-payload` rejects both flags. Upload runs **last**: on create after recipients resolve, on update after the lookup, the sent check, and `buildIntent`, and before the tombstone branch so `createReplacement` (which now sends `intent.fileIDs`, not `[]`) reuses the ids. Each step is an `api.CallOnce` (`files.getUploadURLExternal`, `files.upload`, `files.completeUploadExternal`), so nothing is retried and `--trace` shows three `call` events per file. Orphan policy lives in two functions. `cli.uploadDraftFiles` deletes every id handed out when an upload fails partway (no draft write has happened). `settleUploads` takes the draft write's **raw** error plus the error being reported: `slackRefused` (a typed `SlackErrorResponse`) means the write did not happen, so the files are deleted; anything else (timeout, network, 5xx, rate limit, an unparseable non-envelope body) leaves them and names the ids in `detail`, because deleting under a draft that did get written leaves it a dangling id. A rate limit never counts as a refusal because `postInternal` turns both of its shapes into `*slack.RateLimitedError`. Every other typed `ok:false` code counts, `internal_error` and `fatal_error` included: whether Slack can answer one of those after committing a draft write is unmeasured, and if it can, the delete leaves that draft a dangling id (the reviewer raised it; an allowlist of validation codes is the alternative if it is ever seen). On update every exit of the failed-write branch but the replacement goes through `settleUploads` keyed on the **update's** error, after the re-fetch, so a refused update whose second look shows a tombstone hands the files to the replacement and deletes nothing. A write that succeeded with an unparseable `{ok:true}` body deletes nothing. `deleteUploadedFiles` runs on `context.WithoutCancel(ctx)` plus a 10s deadline (the command's own may be what expired; this is the one place a command deliberately escapes `cli.Context()`), and treats `file_not_found` as deleted. The CLI never deletes a file it did not upload in the same invocation: not the ones `--file`/`--no-files` displace, not on `draft delete`. Rows: `formatDraft` always emits `file_ids` (`[]`, never `null`) and adds `files` (`[{id,name,title,size,filetype,mimetype}]`, empty strings omitted, `file_ids` order) from `draftData.files`, which `joinDraftFiles` fills per response in `fetchDrafts` and `parseDraftWrite`. **Mock-tested only**: the entire CLI path. `draftFileStore` (cmd/draft_files_test.go) models the measured behavior, including `file_not_found` from a draft write for an uncompleted id and an `upload_url` on the same httptest server (slack-go posts to it verbatim), and `runDraftFiles` is a session-token runner that also returns stderr. Mutation-checked: 25 single-line mutations of the upload order, the settle branches, the content rule, and the row shape each fail at least one test. Verified with the installed 6.0.0 on 2026-11-16 (self-DM): create with text and a PDF, create file-only, update keeping files, update replacing with two files (so `drafts.update` answers `{ok, draft, files}`), and the local rejections. Checked in Slack Desktop 2026-11-16 on drafts staged by 6.0.0 in a self-DM: a text draft with a PDF and a txt file, and a file-only draft (the panel shows it as "No message"), both stayed in the open Drafts panel with their file icons, and both sent as messages carrying their files. The cleanup branches, `--no-files`, and the tombstone replacement with files are still mock-tested only. **Unverified**: a scheduled draft with a file, a workspace (T) token, size and blocked-type errors, and what `files.delete` answers for an uncompleted id. Known rough edge, left alone: slack-go's `postWithMultipartResponse` sends a read error on an unbuffered channel nobody receives before the pipe closes, so a file that fails **mid-read** hangs the upload until `--timeout` (found when a mutation let a directory through; the local path check is what keeps a directory or an unreadable file from reaching it).

## Recipients

`draft create` takes a variadic positional `Recipients []string`, not a single `<channel>`. `classifyRecipient` (cmd/draft.go) syntactically sorts each arg into channel vs user: user-shaped is `@name` / email / `Uxxx`-`Wxxx` id / user-profile URL; everything else (`#name`, bare name, `C/D/G/M` id, channel/message URL) is a channel. Bare names stay channels (backward compatible) - a person must be `@name`/email/id. `resolveDestination` then builds exactly one of `channel_id` (one channel recipient, current behavior) or `user_ids` (>=1 user recipient → DM/MPDM that need not exist yet; Slack opens the conversation on send). This is the fix for "can't draft to someone I've never DMed". Mixing channel+user, more than one channel, or `--thread`/`--broadcast` on a user destination are all fatal `invalid_input`. User recipients resolve fully before any write; every unresolved input is reported (`user_not_found`) and aborts - no best-effort, the destination must be atomic. user_ids preserve input order, deduped by resolved id; the caller is NOT auto-added. No local recipient cap (MPDMs cap near 8 - Slack rejects oversized lists; the codebase avoids baking inferred limits into undocumented endpoints). Set exactly one of channel_id/user_ids per destination - `normalizeDestinationsForWrite` strips user_ids only when channel_id is also present (the round-tripped drafts.list shape), which create never produces.
