# Search

Measurements and reasoning behind the rules in `CLAUDE.md`. `CLAUDE.md` holds the current rule for each topic. This file holds how it was found.

## User modifier rewrite

`search messages`/`search files` rewrite `from:@x`, `to:@x`, and `in:@x` to `<@Uxxx>` via `rewriteUserModifiers` (cmd/searchquery.go) before the query ships. Verified live 2026-09-21: Slack's search matches `from:@handle` and `from:<@Uxxx>` (identical rows) but returns an empty page, exit 0, no error, for `from:@Real Name`, `from:@Uxxx`, and `from:"Real Name"`, and `in:@` behaves the same; the CLI's help advertised `from:@user` with no caveat, so an agent read six empty pages as "these people never said it". The rewrite runs every `@` value, plus any quoted `from:`/`to:` value (a quoted `in:` value without `@` may be a channel and passes through), through `ResolveUser` (handle, display name, real name, email, ID all resolve; `<@U…>` and `#chan` values don't start with `@` and pass through), so `from:@Uxxx` gets fixed for free. Unquoted names are greedy to the next `key:` token or quoted token, then the longest resolving prefix wins - one `users.list` load, the rest are map lookups - so `from:@Alice Adams skypilot` needs no quotes. Unresolved names are fatal `user_not_found` with a hint naming the quoted and `<@Uxxx>` forms; a silent empty page was the bug. A failed directory load is not a verdict on the name: `rewriteUserModifiers` returns the resolver's raw error for anything `isInputResolveErr` rejects and `searchQuery` classifies it, so it exits under its own code before any search call. The unquoted prefix loop must return on such an error rather than `continue`, or it tries every shorter prefix against a directory that is down and ends as a false `user_not_found` (`TestRewriteUserModifiers_FailedLookupIsReturnedRaw` pins one lookup). A name several users hold is `ambiguous_user` (`searchAmbiguousUser`, with a hint naming `from:@handle` and `from:<@Uxxx>`), and it ends the prefix loop the same way. `to:` returned no rows in any form against the peers tried, so its rewrite is by analogy with `from:`/`in:`, not verified. To test where a name span stops, use an **unresolvable** name (`TestRewriteUserModifiers_Unresolved`, asserting the error's `Input`): with a resolvable name the longest-prefix fallback hides a broken stop, so the test passes either way.
