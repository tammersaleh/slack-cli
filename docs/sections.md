# Sidebar sections

Measurements and reasoning behind the rules in `CLAUDE.md`. `CLAUDE.md` holds the current rule for each topic. This file holds how it was found.

## section channels and section find name lookups

`section channels` and `section find` read names through `lookupSectionChannels` (cmd/section.go) under the same fail-closed policy as `saved list --enrich`, and both share the bounded worker loop `runBounded` (cmd/bounded.go) with `enrichItems` - first substantive cause kept under a `sync.Once`, siblings cancelled, workers always joined, the caller's own context error returned when nothing else failed. Do not write a third copy. Until 2026-11-10 `resolveChannelNames` dropped every `conversations.info` error: `channels` printed the channel ID as `name` (exit 0, indistinguishable from a real name) and `find` silently skipped the row, so a rate limit changed the output run to run and a name-prefix consumer misfiled hundreds of channels. Now `itemLocalChannelInfoErrors` holds exactly one code, `channel_not_found`; that row is `{id, enrich_error}` with **no** `name` and no `is_archived`, `_meta.error_count` counts the marked rows, and the exit is 1 via `*output.ExitError`. Everything else, including a code Slack has not invented, voids the read: all lookups finish before the first row prints, so the failure is zero rows plus `abortWithTrailer`'s `{"has_more":true,"error":"<code>"}` and a classified stderr error. Each lookup is its own `api.Call`, so a rate limit retries per channel rather than per page (which is what `saved list --enrich` still does). `find` emits an unresolved row whatever the pattern - it matches on the name, so a channel it could not read cannot be ruled out, and dropping it is the old bug. A conversation that resolves with an empty name (a DM) is a success with `"name":""`: detectable, and distinct from a marked row. The lookups stay on the session client (`NewSessionClient`, the E-org token on Grid), which `conversations.info` accepts. `LookupChannel` was not reused: it is best-effort by contract (returns `("", false)` for an error and for a DM alike) and carries no `is_archived`. Measured live 2026-11-10 on a Grid org: a 198-channel section made 198 `conversations.info` calls, all first-attempt, in 2.0s, every row named, exit 0; a 29-channel section took 0.85s. No `channel_not_found` occurred live, so the marked-row path is mock-tested only, and `channel_not_found` being the code Slack returns for a channel in a section that the user can no longer see is from the method docs. `section find` makes one call per channel across **every** section (about 2000 on that sidebar) and was not run live; at that volume a rate limit exhausting its retries now fails the command where it used to drop rows (`todo/section-find-makes-one-conversations-info-call-per-sectioned-channel.md`). `section list` and `section move` were checked for the same pattern and have none: every call's error is classified and returned.

## section rename

`section rename` writes via `users.channelSections.set`, found by probing live 2026-10-16 on scratch sections (`.update`, `.edit`, `.rename` and friends are all `unknown_method`). Form-encoded `channel_section_id` plus `name` and/or `emoji`, bare `{"ok":true}` back. **Any key omitted from the form is cleared on the server**: name-only wiped the emoji, emoji-only wiped the name to "". So rename reads the current emoji from `users.channelSections.list` (which returns `emoji`) and resends it - a read-modify-write, so a concurrent emoji edit between the list and the set can be overwritten; the endpoint offers nothing atomic. Observed semantics: empty `name` is accepted and stored as "" (the command rejects blank names locally as `invalid_input` before any call); surrounding whitespace is stored verbatim, so the name is sent untrimmed and the post-write check is an exact match; renaming to the current name is ok; a name another section holds is `already_exists`, compared case-insensitively; an unknown id is Slack's own `section_not_found`. Because the write answers ok regardless, the command re-fetches and fails `rename_failed` (no row, exit 1) unless both name and emoji match what was sent; the success row comes from the re-fetched data, never the request. The same probe found `users.channelSections.create` answers `invalid_arguments` unless an `emoji` key is present (empty value is fine) - `section create` and `move --new-section` had been failing live since the initial commit, with no test able to notice because `FormValue("emoji") == ""` cannot tell absent from empty. The create tests now assert key presence in `r.PostForm`, and the `sectionStore` mock's `.set` handler uses `r.PostForm` membership to model clear-on-omit. `users.channelSections.delete {channel_section_id}` also works and was used to clean up the scratch sections; not wrapped.

## Section emoji

`section emoji`, `section create --emoji`, and `section move --new-section --emoji` all send the emoji as a **bare name**, exactly as `users.channelSections.list` emits it. Verified live 2026-10-16 on a scratch section (create and set both validate server-side, identically): `heart`, `tada`, `thumbsup`, `+1`, a custom emoji name, `wave::skin-tone-2`, and `wave::skin-tone-6` are accepted and stored verbatim - no alias normalization, so the re-fetch equality check holds; the empty string clears; `:heart:`, `:wave::skin-tone-2:`, `:`, `::`, `::heart::`, `:heart`, `heart:`, `Heart`, `heart ` (trailing space), `wave::skin-tone-1`, `heart::skin-tone-9`, a raw unicode emoji, and an unknown name are all `emoji_invalid` with the section unchanged (every one of these is measured, not inferred). Because `:heart:` is how people type emoji, `normalizeEmojiArg` (cmd/section.go) strips exactly one leading and one trailing colon when both are present and at least one character sits between them (`:heart:` → `heart`, `:wave::skin-tone-2:` → `wave::skin-tone-2`); the strip runs exactly once (`::heart::` → `:heart:`), and `:` and `::` go verbatim - all measured `emoji_invalid`, so a malformed value fails loudly rather than silently clearing the emoji - and nothing else (case, whitespace, unknown names, unicode) is touched - the server is the validator and a local emoji list would rot. The test mock (`emojiAccepted` in cmd/section_test.go) models the measured acceptance as `^[a-z0-9_+-]+(::skin-tone-[2-6])?$`; the 2-6 range is interpolated from the measured endpoints 2 and 6 (1 and 9 rejected), not measured tone by tone. Normalization runs once per user-supplied value - inside `createSection` (shared by `create` and `move`) and in `SectionEmojiCmd.Run` - and never on a value read back from the server, since `rename` feeds `setSection` the emoji it just listed; the stripped value is what the re-fetch compares against and what the row shows. `setSection` is the read-modify-write `rename` already did, now shared: it sends both `name` and `emoji` (omitted keys clear), re-fetches, and returns a `*sectionMismatchError` that `rename` maps to `rename_failed` and `emoji` to `emoji_failed`, so `emoji` fails when the *name* did not survive too. The same race applies to both: a concurrent edit of the other field between the list and the set is overwritten, and the endpoint offers nothing atomic - documented, not designed around. `move`'s `--emoji` is a `*string` so `--emoji ""` without `--new-section` is still `invalid_input` with zero API calls; a plain string cannot tell empty from absent.

## section move

`section move` writes via `users.channelSections.channels.bulkUpdate`, which is **form-encoded** (`PostInternalForm`) with two JSON-string params, NOT a JSON body. `insert=[{channel_section_id, channel_ids:[…]}]` adds channels to a section; `remove=[{channel_section_id, channel_ids:[…]}]` removes them. Verified live 2026-07-09: `remove` pulls a channel out of a section (→ unsectioned); `insert` adds a channel ONLY if it is currently unsectioned - **insert on an already-sectioned channel is silently ignored**. So moving an already-sectioned channel requires insert (target) AND remove (source) in the same call. The old code sent a JSON body `{channel_sections:[{channel_ids_page}]}` (full membership replacement) via `PostInternal`; Slack returned `{"ok":true}` and did nothing - the classic undocumented-endpoint no-op. The command builds one insert for the target and one remove per source section (grouped, sorted by section id for determinism); a channel currently in no section contributes no remove entry, and `remove` is omitted entirely when empty (never send `[]` - unverified). Because the endpoint returns a bare `{"ok":true}` regardless, `moved_count` is NOT the requested count: after the write the command re-fetches sections and counts only channels now in the target and in no other section (`countMoved`). `--section` is validated against the fetched list up front (`section_not_found`) so a typo'd id fails loudly instead of no-opping. Stateful httptest mock in `cmd/section_test.go` (`sectionStore`) reproduces the insert/remove semantics faithfully (remove-then-insert, insert-ignored-while-sectioned) so the round-trip and verified count are actually exercised. Membership completeness: `users.channelSections.list` returns per-section `channel_ids_page` with `channel_ids`, `count`, and a `cursor` (the last channel id). `count` counts all-ever-assigned channels including archived/left ones; `channel_ids` returns only the user's currently-active membership. Verified 2026-07-09: sections like "Maintenance" report `count=70` but 21 active ids (the 49 missing are archived - all 21 returned are non-archived), while active-heavy sections ("INT Customers" 216, "EXT Customers" 191) return their full membership in one page. So `channel_ids` is complete for active channels at these sizes (no low page limit - 216 came back uncut) and `section move`/`list`/`channels`/`find` all operate on it correctly. Latent, unreproduced risk: a section with more *active* channels than the (unknown, >216) page limit would truncate `channel_ids`; there is no dedicated channels.list endpoint (`unknown_method`), and no section command paginates the per-section page. Not worth fixing until a workspace actually hits it.
