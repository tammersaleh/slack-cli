# Output pipeline

Measurements and reasoning behind the rules in `CLAUDE.md`. `CLAUDE.md` holds the current rule for each topic. This file holds how it was found.

## Printer.KeepWhenTrue

`Printer.KeepWhenTrue` (internal/output/output.go) is the value-conditional sibling of `alwaysKeptFields`: keys that survive `--fields` on that printer's rows only while their value is the boolean `true`. `user info` and `user manager-chain` set it to `deleted` (`deactivatedMarker`, cmd/user.go) and nothing else does, so `user list --fields id` still prints `id` alone (`TestUserList_DeletedIsNotStickyUnderFields`). The reason: Slack empties a deactivated account's top-level `real_name`, so `--fields id,real_name` printed `{"real_name":""}`, exit 0, which an agent read as a broken lookup. Putting `deleted` in `alwaysKeptFields` would have made the key sticky on every command and for `false`. No stderr warning and no successor hint, by decision. `manager-chain` rows come from `users.profile.get`, which carries no `deleted`, so `markDeactivated` reads each chain member through `resolver.FetchUser` (cache first, else a traced, retried `users.info`) and adds `deleted: true` only when true; a systemic failure there aborts with the trailer like a failed profile fetch, any other failure leaves the row unmarked. That is one extra request per chain member on a cold user cache.

## Pipeline order and derived fields under --fields

Output pipeline order: `projection.filter` → `enrichTimestamps` → `EnrichFunc` → `projection.dropBorrowed` (internal/output/output.go). Enrichment runs after `--fields` so `--fields user` keeps the resolved `user_name`, and it runs on the projected row so lookups are spent only on ids the caller asked about. A derived name is requestable: `--fields user_name` or `ts_iso` **borrows** the source keys (`user`/`user_id`, `ts`), lets enrichment derive from them, then drops the borrowed keys and any derived key that came only from a borrowed source and was not requested. Until 2026-11-10 the filter kept only keys already in the row, so a derived name selected nothing: `--fields user_name,ts_iso` printed `{}` per row with exit 0 and a healthy trailer, which an agent read as "no results" twice (a participation tally, then ~35 thread reads that lost every speaker). The reverse mapping is not hand-listed: `resolve.EnrichSources()` reverses `enrichUserFields`/`enrichChannelFields` and is wired into `Printer.EnrichSources` beside `EnrichFunc` in `NewPrinter`; `X_iso` reverses by rule through the same `isTimestampKey` that `enrichMap` uses. `TestEnrichSources_CoversEveryNameEnrichAdds` fails when a table entry is added that the reverse mapping misses. Only top-level names reverse: `enrichTimestamps` recurses into nested values and `Enrich` does not, so `--fields latest_reply` returns the object whole with nested `_iso` siblings and no nested names, and a name that exists only nested selects nothing (`TestFields_NestedBehaviorPinned`, written against the old pipeline first). A derived key the command set itself (`date_created_iso`, a preset `channel_name`) goes through the plain path. An unknown name still selects nothing with no error; whether that becomes `invalid_input` or an `unknown_fields` trailer key is undecided (`todo/fields-cannot-name-a-derived-field-and-emits-an-empty-object.md`).
