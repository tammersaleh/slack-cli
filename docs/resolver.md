# Resolver and caches

Measurements and reasoning behind the rules in `CLAUDE.md`. `CLAUDE.md` holds the current rule for each topic. This file holds how it was found.

## Member-first channel-name resolution

Name resolution is **member-first**: `resolveByPagination` scans `users.conversations` (Tier 3, the user's own conversations) before walking `conversations.list` (Tier 2, the whole workspace). Both walks go through the shared `scanForName` helper, same types (`public_channel,private_channel`), `exclude_archived=true`, limit 200. Measured cold (file cache deleted before each run) on a large Enterprise Grid org 2026-07-27, `channel info <name>`, request counts from `--trace` and inclusive of rate-limit retry attempts: two private member channels took 75 and 95 conversations.list requests (76s / 259s) and now take 3 users.conversations requests (2s / 1s); a public member channel now takes 5 (2s); a non-member channel was 64 requests / 192s and is now 6 member + 58 org / 103s; a miss was 190 / 460s (176 pages + 14 retries) and is now 6 + 190 / 462s. The whole member list is 6-7 pages at limit 200, so hits get an order of magnitude cheaper and the miss and non-member paths pay ~6 extra Tier-3 requests, about 2s. Why this matters more than it looks: the file cache is written **only** on a full walk, i.e. only when a name is NOT found, so an early-exit hit persists nothing and *every* cold-process member-name lookup used to pay a partial org crawl. Correctness rules that hold the design together: (1) the member scan's map goes into memory only, via `addChannelsToCache` (first-write-wins, no `saveFileCache`) - the file cache is contractually the complete `conversations.list` snapshot; (2) a member-scan error never aborts resolution, it falls through to the org walk and emits a `fallback` trace event (Grid org tokens get `enterprise_is_restricted`, older OAuth tokens can lack a scope); no context-cancellation special case is needed because the org walk's own `ctx.Err()` check returns the same error before its first request; (3) `scanForName` takes the **first** duplicate-name match, matching the map it builds - the old loop returned the *last* match while caching the first, so a repeat lookup of a duplicated name disagreed with the lookup that populated the cache; (4) only an **exhausted** org walk may call `setChannelMaps` (wholesale replace) and `saveFileCache`. Every other path extends the maps via `addChannelsToCache` (first-write-wins, no eviction): an early-exit hit saw only the pages before the match, and a file-cache hit is a complete but up-to-24h-old snapshot. Replacing in either case evicted names an earlier member scan had already resolved in the same process - typically a channel joined since the snapshot, the exact thing the file cache lacks - turning a resolved channel back into a cache miss and dropping its enrichment name.

## Proven channel-name misses

A proven channel-name miss is answered from memory: `setChannelMaps` sets `channelsComplete`, and `resolveByPagination` returns not-found with zero requests when the maps are complete and `channelsAt` is inside `memoryCacheTTL`. Before 2026-11-10 the resolver stored the exhausted walk's map and then re-walked for the same absent name (176 requests and 460s per miss measured on a large Grid org), so `channel info a b` with both absent paid twice. Completeness is set only by the replace, never by `addChannelsToCache`: a member scan, an early-exit hit, and an enrichment `conversations.info` insert are partial views, and they leave `channelsAt` alone, so they neither grant nor extend the proof. The window is the 5-minute memory TTL on purpose - a channel created after the walk is hidden for minutes, not the file cache's day. The check sits after the file-cache read, which can only add hits. The proof needs both walks: `conversations.list` can omit a conversation the member list holds, so after the replace the exhausted walk merges the member scan's rows back in (memory only), and a member scan that errored clears `channelsComplete` so the next lookup scans again. The first build skipped both and would have reported a member-only channel absent for five minutes after any miss (caught in review; `TestResolveChannel_ProvenMissKeepsMemberOnlyChannels`, `_FailedMemberScanDoesNotProveAMiss`, each confirmed failing with the merge removed). Process-local only: the file cache carries no completeness flag, so a second invocation walks again (`todo/a-proven-miss-is-never-cached.md`).

## exclude_archived page shrinkage

`exclude_archived` shrinkage on `conversations.list` is real but **not worth working around** (measured 2026-07-27, same Grid org, limit 200, full `--include-non-member` walk): `exclude_archived=true` returned 5330 channels in 176 requests (30/page); `exclude_archived=false` returned 16805 in 175 requests (96/page) of which 5698 were unarchived. Slack picks a fixed candidate window per request and filters after, so fetching archived rows to get fuller pages buys **1 request out of 176** while tripling the bytes. Page size does track `--limit` though (first page, exclude_archived: 13 items at limit 50, 26 at 100, 48 at 200; latency flat at ~320-360ms), so `--limit 200` roughly halves request count for a bulk `--include-non-member` walk. That stays opt-in - the `--limit` flag help now explains the shrink - rather than a sentinel default, which would change what one page means for anything scripting the current default. The resolver already used limit 200.

## Channel enrichment is a single fetch

Channel cache enrichment: `Enrich` resolves a `channel_id` via `LookupChannel`, which mirrors `LookupUser` - in-memory cache hit, else a single `conversations.info` call. It does NOT bulk-load `conversations.list`. This was the cause of a multi-minute hang: on a cold channel cache, naming the one channel in a `thread list`/`saved list` output used to paginate the entire workspace via `conversations.list` (Tier-2, rate-limited - ~13 min on a large Enterprise Grid org). `LookupChannel` failures are memoized per-process in `failedChannels` so a wide result set with an unresolvable ID doesn't re-hit `conversations.info` per row (this replaced `ensureChannelCache`'s empty-attempt storm guard). `addChannelToCache` only touches in-memory maps - it never calls `saveFileCache`, so a sparse enrich-time entry can't be persisted as if it were the complete `conversations.list` snapshot. Cache-completeness is safe because every `r.channels` read returns only on a name *hit* and never treats a miss as authoritative. `LookupChannelName` stays the pure cache read; `LookupChannel` is the networked path. Cost model: O(distinct unresolved IDs in output), not O(workspace size).

## bulkLoadUsers

`bulkLoadUsers` (internal/resolve/user.go) walks `users.list` through `api.Paginate` over `GetUsersPaginated`, limit 200, a fresh `slack.UserPagination` per attempt with every option reapplied (the paginator carries its cursor, as in `user list`). It replaced slack-go's `GetUsersContext`, which pages internally and sleeps through every 429 with no callback and no attempt cap: a cold email lookup on a large Grid org measured about ten minutes with zero `--trace` lines (2026-10-12), which read as a hang. The walk now emits a `page` event per request and a `retry` per wait, and gives up after 5 attempts on one page. An exhausted walk used to read as `user_not_found` because `ResolveUser` discarded `ensureUserCache`'s error. It now returns it (see the user resolver errors bullet), so the cap surfaces as `rate_limited`, exit 3, `endpoint: users.list`. Nothing is cached unless the whole walk succeeds. Email order is cache (bulk load when stale) first, `users.lookupByEmail` only for an email the cache lacks - the `user info` help claimed the reverse until 2026-11-10. The cold walk has not been re-measured live since the swap; page and retry counts on a large org are still unrecorded.

## Cold users.list walk measurement

The cold `users.list` walk was measured on the installed 5.13.0 against a large Enterprise Grid org 2026-11-10 (`SLACK_CACHE_TTL=1ns slack --trace user info @<absent-handle>`): 42 pages at limit 200, 10 seconds, zero `retry` events, exit 1 with one `user_not_found` row. The ten-minute cold lookups in the October work orders were slack-go's `GetUsersContext` sleeping through 429s, or several sessions refreshing at once, not the directory's size. One run does not prove a page never exhausts its 5 attempts, so the swallowed bulk-load error in `ResolveUser` is still a real gap. An absent `@handle` is the cheap way to force the walk without putting anyone's email in a command line.

## Single-ID lookups: LookupUser, LookupChannel, FetchUser

Single-ID lookups (`LookupUser`, `LookupChannel`) are `api.Call`s: a `call` trace event each and the shared rate-limit retry. They run inside the printer's emit path, so the retry is bounded by a per-method stop: once `users.info` or `conversations.info` returns `*api.RateLimitExhaustedError`, the resolver sets `usersInfoDown`/`conversationsInfoDown` and every later uncached lookup of that method returns without a request. Without it each distinct uncached ID in an output would wait out its own four `Retry-After` sleeps. Worst case is one exhausted run per method per process, and `--timeout` still cuts it short. Other failures are memoized per ID (`failedUsers` holds the error, `failedChannels` a set); a dead context is memoized nowhere, since it says nothing about the ID and `api.Call` spends no request on one. `LookupUser` returns the error with every `found=false`, and `Enrich` drops it. **`LookupUser` is the best-effort entry point and `FetchUser` is the one for a command whose answer is the user** (`user info`, `status get`): same cache, same traced retrying request, but `FetchUser` never consults the memo or the stop. Sharing one entry point (the first build, caught in review) let an exhausted `--full` manager-name lookup refuse the next input's primary fetch and abort the run, and let a transient error memoized by enrichment replay as that user's verdict. `FetchUser` replaced cmd's `fetchUser`, which called `users.info` itself after the resolver's swallowed attempt, so a cache miss now costs one request, not two. Still missing: a row that lost its name carries no marker (`todo/enrichment-users-info-fallback-is-untraced-and-unretried.md`).

## User name ranking

User name ranking (internal/resolve/user.go, `userIDByName`). Until 2026-11-10 one `usersByName` map held handles, display names, and real names, first-write-wins over Go map iteration, so a shared name returned a different user per process, exit 0, and a deactivated duplicate could win (on a large Grid org: 177 shared name keys, 95 of them between two or more active accounts). Now `usersByHandle` and `usersByLabel` (display name and real name) are `map[string][]string` holding every candidate, and the ranking runs **at lookup** from the user records, so insertion order cannot matter on either the bulk or the single-insert path. Rules, in order: the handle tier beats the label tier outright, a deactivated handle included, because the handle is the one name that asks for a specific account; within the winning tier active accounts drop the deactivated ones; one left is the answer; two or more is `*resolve.AmbiguousUserError` with the candidates sorted by ID. Two deactivated accounts tied with no active holder are ambiguous too. Bots and app users rank like anyone. Matching stayed exact and case-insensitive on `name`, `profile.display_name`, and top-level `real_name` - `profile.real_name` is still not indexed, so a deactivated account (whose top-level `real_name` Slack empties) is findable by display name and handle only. `usersByEmail` got the same treatment for the never-observed shared email: active first, then lower ID (`outranks`). The file cache stores users, not an index, so its format did not change and an old file answers under the new rules (`TestResolveUser_FileCacheFromAnEarlierRelease`). `usersComplete` is the user-side `channelsComplete`: before it, a users.info insert made `ensureUserCache` treat a one-user map as the directory for five minutes, so a name could resolve to a deactivated account just because it was fetched first, or miss a second holder. `ensureUserCacheLazy` returns early on that partial map (it must stay cheap: `cachedUser` calls it per `LookupUser`), so `ensureUserCache` reads a fresh file cache itself before it falls back to the `users.list` walk. The cmd side is `ambiguousUserError` (cmd/resolve_errors.go) mapping to `output.AmbiguousUser`, which carries `candidates` (`id`, `name`, `title`, `deleted` only when true) both in `detail` and as a field; `candidates` is in `alwaysKeptFields`. `isInputResolveErr` counts it as a verdict on the input, so the row commands print it as that input's row and everything using `userResolveError` fails before its first write. Two sites needed their own code: `draft create` returns the ambiguity at once instead of folding it into the joined `user_not_found` list, and the search rewrite's unquoted prefix loop returns on it - falling through would resolve `from:@Alice Adams` to whoever holds the handle `alice` (`TestRewriteUserModifiers_AmbiguousSpanDoesNotFallBackToAShorterOne` asserts the lookups stop). Verified live 2026-11-10, read-only: a name shared by an active and a deactivated account gave the active one on 6 of 6 runs, a name shared by two active accounts gave `ambiguous_user` with 2 candidates on `user info` and on `search messages`, and a label that is also another account's handle resolved to the handle's account. Tests build 50 resolvers per ranking case because map order is per-range, give every candidate a different outcome, and run all insertion orders on the single-insert path; mutating the tier order, the active filter, the sort, the tie error, or `usersComplete` each fails them.

## Slack URL input

Slack URL input: `internal/slackurl` is a pure, route-aware parser (`Parse(s) (Ref, matched, err)`). Route picks the `Kind` (channel/message/user/file); the prefix letter only validates the extracted id. Tri-state result: `matched=false` = not a URL (caller falls through to ID/name handling); `matched=true, err!=nil` = URL-shaped but unusable (caller fast-fails, no pagination). A file URL embeds a uploader `U…` *and* an `F…`, so kind must come from the route, not a prefix scan. ts comes from the `p<digits>` segment (last 6 = micros); `thread_ts`/`cid` are validated and `cid` must match the path channel. `/lists/<team>/<F…>` parses as Kind file (a Slack List is a file); the team segment is ignored because it is the org id in a URL copied from the client and the workspace id in the permalink Slack returns.

## Channel resolver errors

Channel resolver errors are three kinds, and only one means "no such channel": `resolve.ErrBadURL`, `resolve.ErrNotFound` (a clean miss: an exhausted `conversations.list` walk, the proven-miss memo, or an ID of another kind), and the raw error of the `conversations.list` walk that failed. `cli.channelResolveError` maps the first to `invalid_input`, the second to `channel_not_found`, and sends everything else through `cli.ClassifyError`, so a bad token exits 2, an exhausted rate limit exits 3 with its `endpoint`, and `enterprise_is_restricted` keeps its name. Before 2026-11-10 the helper mapped every non-URL error to `channel_not_found` with a hint to browse the channel list, which is how a Grid token-context problem was reported as a missing channel. The member scan's error is still never returned: the org walk is the final authority, so a failed `users.conversations` plus an exhausted `conversations.list` is `ErrNotFound`. The mapper is a method because it needs the auth-method hint, and that makes `cli.authMethod` matter during resolution: the two-client commands (`channel managers`, `draft create`, `list record add`/`update`) restore the session method right after `NewClient`, so they capture the workspace method first and classify a failed lookup under `cli.withAuthMethod(workspaceAuthMethod, ...)`. Policy per call site, all fail-closed (`isInputResolveErr` is the only gate to a per-input row or a passthrough, so an unenumerated error stops the command): single-channel commands (`channel members`/`managers`, `message list`/`permalink`, `thread list`, `pin list`, `bookmark list`, `draft create`, `list record` channel values) and `resolveRefChannels` (`message get`, `reaction list`) are fatal on any failure with nothing on stdout; `channel invite`/`kick` are fatal through `resolveAll`; `channel info` resolves every input up front through `resolveInputs`, prints a clean miss or bad URL as that input's row in input order, and on a failed lookup prints only the `abortWithTrailer` trailer (no rows, zero `conversations.info` calls); `file list --channel` passes a clean miss through to `files.list` as typed and is fatal on a bad URL or a failed lookup. Tests: cmd/resolve_errors_test.go runs every channel-name command against both an auth failure and a clean miss, plus an exhausted rate limit on the org walk (one 4-second run of retries, the member scan answers cleanly so it is not two). Mutation-checked: making the mapper return `channel_not_found` for everything fails 16 of them, and classifying `channel managers` under the ambient method fails the hint test.

## User resolver errors

User resolver errors follow the same three kinds (`ErrBadURL`, `ErrNotFound`, raw), mapped by `cli.userResolveError`. `ResolveUser` discarded the directory walk's error on both branches until 2026-11-10, so no helper could recover it. The rules now: a name is a clean miss only when the directory loaded without it, and a failed load is returned wrapped (`errors.As` still finds the `RateLimitExhaustedError` and its `endpoint`); an email is a clean miss when the directory loaded without it and `users.lookupByEmail` answered `users_not_found`, and any other answer from that call is returned raw (the todo's rule, and what `TestUserCommands_ResolveSystemicAbortWritesTrailer` already pinned); an email whose directory load failed still tries `users.lookupByEmail` and a hit answers, but a miss there returns the **load's** error, because that endpoint does not see every account the directory holds and its `users_not_found` proves nothing alone. Policy per call site: `user info`, `user manager-chain`, `status get`, `presence get`, and `dnd info` resolve every input up front through `resolveInputs` (cmd/resolve_errors.go), print a clean miss or bad URL as that input's row, and on a failed lookup print only the `abortWithTrailer` trailer with zero rows and zero further requests - `systemicResolveError` and its exit-code allowlist are gone, replaced by `isInputResolveErr`, which is fail-closed (an unenumerated error stops the command instead of becoming a row); `channel invite`/`kick`, `file list --user`, and `list record` user values are fatal on any failure; `draft create` still collects every clean miss into one `user_not_found` but returns a failed lookup at once under its own code; search is described in its own bullet. User lookups in the two-client commands run on the session client, whose auth method is the ambient one, so they need no `withAuthMethod`. The second verdict on the input, `ambiguous_user`, is wired exactly there: a typed error from `userIDByName` (internal/resolve/user.go), a case in `cli.userResolveError`, and a clause in `isInputResolveErr`. Tests: internal/resolve/user_errors_test.go tables every combination of directory and `lookupByEmail` outcome, and cmd/resolve_errors_test.go counts requests besides `users.list` to prove the abort asks Slack nothing else. `isEmail` rejects any input holding whitespace: the search prefix loop offers spans like `bob@example.com deploy now`, which used to be email-shaped, cost a `users.lookupByEmail` call per prefix, and since that call's non-miss errors now surface could abort the search on whatever Slack makes of a malformed address (the reviewer caught it; Slack's actual answer was not measured). Mutation-checked three ways: restoring the discard in `ResolveUser` fails 17 tests, flattening the mapper fails three groups, and letting the search prefix loop `continue` on any error fails the search cases. The up-front pass changes one observable thing for these five commands: a run that would have printed good rows and then aborted on a later input's lookup now prints none.
