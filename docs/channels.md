# Channels

Measurements and reasoning behind the rules in `CLAUDE.md`. `CLAUDE.md` holds the current rule for each topic. This file holds how it was found.

## channel list endpoint sourcing

`channel list` sources its two modes from **different endpoints**, and that choice IS the member filter - there is no client-side membership check left in the command. Default → `users.conversations` (only the user's own conversations, Tier 3); `--include-non-member` → `conversations.list` (the whole workspace, Tier 2). `channelSource` (cmd/channel.go) binds endpoint name + fetch + row normalization together so the three can't drift. Measured on a large Enterprise Grid org 2026-07-27: default is 19 requests / ~5s at the real `--limit 100` default (10 requests / 3.5s at limit 200), against 178 requests / 8m15s / 5699 channels for the full `conversations.list` walk - the old default paginated all 5699 to emit 1787. Verified live before shipping, all on a desktop `xoxc` token against the T-workspace: (1) `users.conversations` **omits `is_member` entirely on the wire** for every type - raw-JSON checked, not just the decoded struct - so slack-go zeroes it and the printer would emit `is_member:false` for channels the user is plainly in; `normalizeUsersConversations` reports `true` for every row except `im`. Group DMs get `true` because being in one is a real membership and `conversations.list` is documented to report it as such (unverifiable on this org - it returns no mpims at all, see below); `im` keeps `false` because Slack sends no `is_member` for a 1:1 DM on either endpoint (raw-JSON checked on both), so there is no value to report and `false` is what this command has always emitted for DMs. (2) It also omits **`num_members`**, which `conversations.list` does send; the key is deleted rather than emitted as a false `0`. Those two are the only key differences between the endpoints' public-channel payloads. (3) The full ID-set diff explains both directions: +271 rows are group DMs (`conversations.list` returns **zero mpims** on this org even with `types=mpim`, so the old default omitted every group DM), and -18 rows are DMs whose user is **deactivated** (all 18 confirmed `deleted=true`; `is_open` is false for all 349 IMs `users.conversations` returns, so openness is not the discriminator). Zero non-member leakage: every uc row that `conversations.list` also returned had `is_member=true`. (4) Each `--type` works alone and the four single-type walks union **exactly** to the combined walk (1787, no dupes). (5) `exclude_archived=false` is a proper superset (608 vs 587 private). (6) Pages do not shrink under `exclude_archived` the way `conversations.list` pages do (193/191/193 of 200). (7) On the E-prefix org token `users.conversations` fails `enterprise_is_restricted` - but so does `conversations.list`, so no regression; `channel list` uses the T-workspace client either way. Scopes are unchanged (`channels:read,groups:read,im:read,mpim:read` already in `botScopes`), though only the session-token path was exercised live - an OAuth `xoxb` run is unverified. `UserID` stays empty (= the token's actor), which preserves whose membership is listed.

## channel list --has-unread

`channel list --has-unread` reads unread state from the **undocumented internal** `client.counts`, not any list endpoint. Neither `conversations.list` nor `users.conversations` returns `unread_count` at all (raw-JSON checked), so the old filter compared a never-populated Go zero value and silently matched nothing - an agent asking "what's unread" was told "nothing". `fetchUnreadState` (cmd/channel.go) makes one `PostInternal` call and builds an id→state map before streaming starts, because `streamPages`' emit callback may not do network calls. Rows that match carry `has_unreads`/`mention_count`/`last_read` so the caller can see what it filtered on. Verified live 2026-07-27 against a Grid org: buckets are `channels`/`mpims`/`ims` (also `threads`, and `file_channels` which is an object not an array - unmarshal it as `[]row` and you get a type error); every public and private channel the user is in is present (1168 of 1168); `has_unreads` agreed with `latest > last_read` on all 1194 rows; DMs appear only while open (22 of 271 mpims, 64 of 350 ims), so **absent means no unread badge, not unknown** - which matches Slack's own sidebar. End-to-end the emitted set is exactly (conversations you're in) ∩ (unread per counts): 24 = 24 with zero unread conversations missing from the listing. Needs a session token, and on Grid the **E-org** context - the T-workspace token returns `team_is_restricted` on this endpoint, the mirror image of `users.conversations` failing `enterprise_is_restricted` on the E token. So `--has-unread` uses the same two-client split as `channel managers`, including capturing the session auth method before `NewClient` clobbers it. A bot token fails `session_token_required` (exit 2) rather than filtering on nothing.

## channel managers

Channel managers (`channel managers`, the "Managed by" list in the About tab) come from the **undocumented internal** `admin.roles.entity.listAssignments` (`entity_id=<channel>`), NOT any public API. `conversations.info` has no managers field, and the public `admin.roles.listAssignments` is org-admin gated (`invalid_actor` for a member token); the `.entity.` variant works with a plain member session token, so it follows the `PostInternalForm` pattern. Response: `{role_assignments:[{role_id, users:[…]}]}`. `Rl0A` is the Channel Manager role (observed via the Slack web client 2026-06-10). The command emits every returned assignment's users verbatim with `role_id` - it does NOT hard-filter to `Rl0A`, since a wrong/stale ID would silently report no managers (the worst failure for an undocumented endpoint); no human `role` label (the mapping is undocumented and would rot). Two-client split is mandatory on Enterprise Grid: the session client (E-org token, `NewSessionClient`) backs the internal call, but channel-*name* resolution uses the public client (T-workspace token, `NewClient`) because `conversations.list` is `team_is_restricted` on the org context. Order matters: `NewClient` clobbers `cli.authMethod`, so the command captures the session auth method and restores it before any `ClassifyError` on the internal call. No `slack_route` param needed (verified live). One row per assignment per user, no dedupe; empty list is success not an error.

## channel invite and channel kick

`channel invite` / `channel kick` (cmd/channel_membership.go) are the channel membership writes (`channel create`, below, is the other channel mutation). Mixed variadic recipients go through the same `splitRecipients`/`classifyRecipient` as `draft create` (now in cmd/recipients.go): `@name`/email/`U…`/profile URL is a person, everything else a channel, at least one of each. Everything resolves before the first write (`resolveAll`, dedupe by resolved id, first-seen order); a miss aborts with no rows and no calls. Then **one `api.Call` per (channel, user) pair**, sequential, channels outer - batching `users` on `conversations.invite` was rejected because its partial-failure semantics are unverifiable without a real invite (Slack documents a `force=true` for it, and slack-go does keep `errors[]` in `SlackErrorResponse.Errors`), it would make invite structurally unlike kick, and the workflow that filed this is one user across hundreds of channels. `api.Call` is the single-shot sibling of `FetchPage` on the shared `retry` loop and emits `call` trace events, not `page`. Rows are `{channel_id,user_id,status|error}` so enrichment names both sides. Error dispositions are **explicit allowlists, fail-closed** (`membershipOp.pairErrors`/`channelErrors`, confirmed against the method docs 2026-10-19): the idempotent code (`already_in_channel`; `not_in_channel` on kick, where it means the target) is a `status` and exits 0 so re-runs are safe; a pair code marks one row; a channel code (`not_in_channel` on invite means the caller, `is_archived`, `channel_not_found`, `cant_kick_from_general`, `method_not_supported_for_channel_type`) marks every remaining user in that channel with no further calls; **everything else aborts**, including `no_permission`, `restricted_action`, `missing_scope`, and any code Slack has not invented yet - treating an unknown code as pair-local would multiply a systemic failure across the matrix. A fatal abort prints `{"_meta":{"has_more":true,"error":"<code>","error_count":N}}` with no cursor: rows already emitted are authoritative and the recovery is to rerun the idempotent command. Verified live 2026-10-19 with side-effect-free probes (inviting/kicking self): the desktop session token reaches per-user validation (`cant_invite_self`, `cant_kick_self`) on a private channel on both the T and E contexts, so no two-client split; `errors[]` has one entry per user and is absent for a channel-level `channel_not_found`. OAuth bot scopes added: `channels:manage,groups:write` (kick's requirement, which also covers invite; the granular `*:write.invites` would add consent text without reducing authority, and `im:write`/`mpim:write` are pointless since both methods answer `method_not_supported_for_channel_type` on DMs). `missing_scope` is fatal here and exits 2 (it is in `authErrors`). An actual end-to-end invite was **not** run; only error paths were exercised live.

## channel create

`channel create <name> [--private]` (cmd/channel_create.go) is `conversations.create` on the **workspace client** (`NewClient`), one request, one row from the returned channel object (`channelToMap` minus `num_members`, which the create response does not send), then the trailer. Scope is minimal by decision (Tammer, 2026-11-10): no `--invite`, topic, purpose, or description, and the caller composes `channel invite`. Measured live 2026-11-10 on an Enterprise Grid org with a desktop session token, two private scratch channels created and archived, every other probe a request that could not create. Token context: the T-workspace token creates with no `team_id`; the E-org token answers `cannot_create_channel` without `team_id` and reaches name validation with `team_id=<T id>` (`invalid_name_required`, `name_taken`), but a create on the org path was not run. Name rules, each measured: empty is `invalid_name_required`, a 95-character name `invalid_name_maxlength` (80 is the documented limit, the boundary itself was not probed), uppercase or `!`/`?` `invalid_name_specials`, hyphens only `invalid_name_punctuation`, a `name` param absent altogether `invalid_arguments`. Slack does **not** lowercase: an uppercase name is rejected, so the stored `name` equalled the requested one in every success and `name_normalized` matched it. `name_taken` is one namespace: the same name asked for as public, asked for through the org token, and asked for after the channel was archived all answered `name_taken`. The response channel has `is_member: true`, `is_private: true`, `is_archived: false`, empty topic and purpose objects, `context_team_id` and `shared_team_ids` naming the workspace, and no `num_members` (`channel info` reports 1). The CLI strips one leading `#` and touches nothing else, the section-emoji rule: the server validates, and lowercasing locally would create a channel the caller did not ask for. The request goes through `api.CallOnce` (internal/api/call.go), the no-retry sibling of `api.Call`: same `call` trace event, always `attempt` 1, a rate limit returned bare so it classifies `rate_limited` exit 3 without an "after 5 attempts" claim. It is not retried because nothing measured says a 429 means the request did not run, and a repeat of a create that ran answers `name_taken`, a failure report for a channel that exists. `channelCreateHint` attaches hints for Slack's own codes, and an unlisted code passes through with none. `unknownCreateOutcome` (`rate_limited`, `timeout`, `network_error`, `http_error`, `parse_error`, `unknown_error`) gets the "may or may not exist, check `channel info`" text **in front of** the classifier's own hint, because a 200 with an unreadable body or a 5xx can follow a create that committed. A `--timeout` that expires before the request is sent gets no such text (`sent` is set inside the `CallOnce` closure). All errors are fatal on stderr with empty stdout, the `section create` shape, not `abortWithTrailer`: there are no rows to protect. slack-go's `CreateConversationContext` drops `response_metadata.messages`, so an `invalid_arguments` detail would be bare, but the CLI always sends `name` and cannot reach it. `botScopes` already holds `channels:manage` and `groups:write`. Unverified: a public create, any create on an OAuth bot token, `restricted_action` and the guest codes (hints written from the method docs), and the org-token create. `TestChannelCreate_UsesWorkspaceToken` pins the client choice with `runWithTwoCredentials`. To archive a scratch channel, send `conversations.archive` (`channel=<id>`) from the probe module on the workspace token: it answered `{"ok":true}` and `channel info` then showed `is_archived: true`.
